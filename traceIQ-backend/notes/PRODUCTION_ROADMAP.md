# TraceIQ — Production Readiness Roadmap

This document is the master plan for taking TraceIQ from "working mini-project" to
"production-grade, dynamic-detection SaaS platform." It consolidates every gap found
during the architecture review of the detection engine, the LangGraph AI agent, the
Operational RAG pipeline, and the frontend.

It continues the phase numbering used in `traceIQ-backend/notes/phaseN.txt` (the project
left off at Phase 6 — Redis Caching). Phases 7+ live here because they span both repos.

---

## 0. How to use this document

Each phase lists: **Problem → Why it matters → Fix → Files touched → Effort**.
Work top-to-bottom within a phase; phases are ordered by priority, not by convenience.
Phases 7 and 8.2/8.3 should be done before anything else — they are security bugs, not
polish.

## Priority / effort legend

| Priority | Meaning |
|---|---|
| P0 | Security or correctness bug. Fix before adding anything new. |
| P1 | Structural gap that blocks "production-grade" claims. |

## Phase 7 — Critical Security & Correctness Fixes (Backend)

### 7.1 [P0, S] AI agent tools ignore server-side tenant scoping

**Problem**: Every tool in [ai.tools.ts](traceIQ-backend/src/modules/ai/tools/ai.tools.ts)
declares `tenantId` as an LLM-fillable Zod parameter. The controller resolves the real
tenant from the JWT ([investigation.controller.ts:13](traceIQ-backend/src/controllers/investigation.controller.ts:13))
and puts it in graph state, but nothing stops the model from passing a *different*
`tenantId` when it calls `exact_search` / `semantic_search` / `get_timeline` / `get_detections`.

**Why it matters**: This is a cross-tenant data leak waiting to happen — via model error,
or via indirect prompt injection (event `metadata` is attacker/customer-controlled, gets
embedded in tool output, and is fed back into the model's context on the next loop turn).
In a security-audit product this is the worst possible bug class.

**Fix**: Remove `tenantId` from every tool's Zod schema. Build the tools as a factory
that closes over the tenantId resolved server-side, and construct them per-investigation
inside the orchestrator instead of exporting static module-level tools.

```ts
// tools/ai.tools.ts
export function buildToolsForTenant(tenantId: string) {
  const exactSearchTool = tool(
    async ({ actor, action, limit }) => { /* tenantId comes from closure, not args */ },
    { name: 'exact_search', schema: z.object({ actor: z.string().optional(), ... }) }
  );
  // ...same for the other 3 tools
  return [getDetectionsTool, exactSearchTool, semanticSearchTool, getTimelineTool];
}
```

`investigation.graph.ts` and `ai-orchestrator.service.ts` need to build the graph (or at
least the `ToolNode`) per-invocation with the scoped tools, instead of importing a
singleton `allTools`.

**Files**: `src/modules/ai/tools/ai.tools.ts`, `src/modules/ai/graph/investigation.graph.ts`,
`src/modules/ai/services/ai-orchestrator.service.ts`.

### 7.2 [P0, S] `/auth/register` allows joining *any* tenant by UUID guess

**Problem**: [auth.routes.ts:18](traceIQ-backend/src/routes/auth.routes.ts:18) exposes
`POST /register` publicly, unauthenticated. Its schema
([auth.types.ts:3-7](traceIQ-backend/src/types/auth.types.ts:3)) accepts a caller-supplied
`tenantId` with no verification that the caller has any relationship to that tenant.

**Why it matters**: Anyone who obtains or guesses a tenant UUID (they appear in JWTs,
logs, screenshots, etc.) can self-register a `VIEWER` account into that tenant and read
its audit trail. This is a full multi-tenancy bypass, arguably worse than 7.1.

**Fix**: Two valid designs — pick one and note the decision in this doc:
- **Invite-only (matches current login copy "Account access is granted by your Tenant
  Admin")**: require a signed, single-use invite token (email + tenantId + role, HMAC-signed,
  short TTL) generated by a `TENANT_ADMIN`-only endpoint. `/register` validates the token
  instead of trusting a raw `tenantId` from the body.
- **Self-serve signup**: `/register` creates a *new* `Tenant` + its first `TENANT_ADMIN`
  user in one transaction; it never accepts an existing `tenantId` from an unauthenticated
  caller. Joining an *existing* tenant still requires the invite-token flow above.

Given Phase 12 below adds a real onboarding funnel, recommend doing **both**: self-serve
tenant creation for new customers, invite tokens for adding teammates to an existing tenant.

**Files**: `src/routes/auth.routes.ts`, `src/controllers/auth.controller.ts`,
`src/services/auth.service.ts`, `src/types/auth.types.ts`, new `invite.repository.ts` /
`Invite` Prisma model.

### 7.3 [P0, S] No RBAC gate on `/api/v1/ai/investigate`

**Problem**: [investigation.routes.ts](traceIQ-backend/src/routes/investigation.routes.ts:8)
only applies `jwtAuthMiddleware`. `rbac.middleware.ts` exists but isn't used here — any
authenticated role, including `VIEWER`, can trigger an LLM investigation.

**Fix**: Add `rbacMiddleware(['TENANT_ADMIN', 'AUDITOR', 'ANALYST'])` (exclude `VIEWER`).
Also add a per-tenant rate limit on this route specifically — it's the most expensive
endpoint in the system (multiple OpenAI calls per request).

**Files**: `src/routes/investigation.routes.ts`.

### 7.4 [P0, S] Brute-force detection window never actually expires correctly

**Problem**: [detection.rules.ts:15-17](traceIQ-backend/src/modules/detection/detection.rules.ts:15)
uses `LPUSH` + `EXPIRE` on the same key. `EXPIRE` resets the TTL on the whole key on every
push, so a slow drip of failures (e.g. one every 9 minutes) keeps the key alive
indefinitely — "5 failures in 10 minutes" silently becomes "5 failures, whenever."

**Fix**: Replace the list with a Redis **sorted set** keyed by event timestamp (score),
trim on read:

```ts
const now = Date.now();
await ctx.redisClient.zadd(redisKey, now, ctx.eventId);
await ctx.redisClient.zremrangebyscore(redisKey, 0, now - WINDOW_MS);
await ctx.redisClient.expire(redisKey, WINDOW_MS / 1000); // safety net only
const failureCount = await ctx.redisClient.zcard(redisKey);
```

Extract this into a shared `slidingWindowCounter(redis, key, windowMs)` helper so future
stateful rules (and Phase 9's baselining) don't reimplement it per rule.

**Files**: `src/modules/detection/detection.rules.ts`, new
`src/modules/detection/sliding-window.util.ts`.

### 7.5 [P0, S] `AFTER_HOURS_ADMIN_ACTIVITY` trusts caller-supplied role

**Problem**: [detection.rules.ts:79](traceIQ-backend/src/modules/detection/detection.rules.ts:79)
reads `event.metadata?.role` — whatever the ingesting service claims. Any client posting
to `/api/v1/events` can set or omit this field, bypassing the rule entirely or triggering
false positives at will.

**Fix**: Resolve role server-side. If the actor string corresponds to a known TraceIQ
`User`, use `user.role`. If actors can be non-human/service accounts with no `User` row,
maintain an explicit tenant-scoped "privileged actors" list instead of trusting inbound
metadata. Also replace the fixed `8–18` local-server-hours check with a per-tenant
timezone setting (`Tenant.timezone` column) — otherwise this rule is simply wrong for any
tenant not in the server's timezone.

**Files**: `src/modules/detection/detection.rules.ts`, `prisma/schema.prisma` (add
`Tenant.timezone`).

## Phase 8 — AI Agent & Operational RAG Hardening

### 8.1 [P1, L] Semantic search doesn't scale past a demo dataset

**Problem**: [ai.tools.ts:88-104](traceIQ-backend/src/modules/ai/tools/ai.tools.ts:88) pulls
the 500 most-recent tenant events into Node and computes cosine similarity by hand, per
query. This only searches recent events (a semantically relevant event from last month is
invisible) and is O(N) with zero indexing — the opposite of what an audit-log product
needs at real volume.

**Fix**: Migrate to `pgvector`.
1. `CREATE EXTENSION vector;`
2. Change `AuditEvent.embedding` from `Float[]` to `Unsupported("vector(1536)")` (Prisma's
   pgvector support) or drop to raw SQL for this column via a migration.
3. Add an HNSW index: `CREATE INDEX ON audit_events USING hnsw (embedding vector_cosine_ops);`
4. Rewrite `semanticSearchTool` to do the similarity search in SQL:
   `... ORDER BY embedding <=> $1 LIMIT $2` scoped by `tenantId`, replacing the manual
   `cosineSimilarity()` loop entirely.
5. Keep a fallback path for events with a null/zero embedding (failed OpenAI calls — see 8.4).

**Files**: `prisma/schema.prisma`, new migration, `src/modules/ai/tools/ai.tools.ts`
(delete `cosineSimilarity`, rewrite `semanticSearchTool`).

---

### 8.2 [P1, S] No caps on agent tool inputs or loop iterations

**Problem**: `limit` in `exact_search` / `get_timeline` is `z.number().optional()` with no
max — the model can request unbounded rows. The investigator↔tools loop in
[investigation.graph.ts](traceIQ-backend/src/modules/ai/graph/investigation.graph.ts) has
no `recursionLimit` or step budget, so a model that keeps issuing tool calls can run cost
up indefinitely on a single request.

**Fix**:
- `limit: z.number().int().min(1).max(100).optional()` on every tool.
- Pass `{ recursionLimit: 8 }` (tune) to `investigationGraph.invoke(...)` in
  `ai-orchestrator.service.ts`.
- Track a per-investigation tool-call counter in state; short-circuit to the reporter node
  if exceeded, so a runaway loop still produces a (partial) report instead of erroring out.

**Files**: `src/modules/ai/tools/ai.tools.ts`,
`src/modules/ai/services/ai-orchestrator.service.ts`,
`src/modules/ai/graph/investigation.state.ts`.

---

### 8.3 [P1, M] Agent runs are unobserved and untraceable

**Problem**: In a compliance/audit product, the AI agent's own actions (which tools it
called, with what arguments, over what evidence) aren't logged or queryable anywhere. If
an investigation report is later challenged, there's no way to reconstruct why the agent
concluded what it did.

**Fix**:
- Add a `AgentRun` / `AgentTrace` Prisma model: `investigationId, tenantId, query,
  toolCalls (Json), finalReport (Json), durationMs, tokenUsage (Json), createdAt`.
- Persist the full `messages` array from final graph state after each `investigate()`
  call — this *is* your compliance trail for the AI feature.
- Optionally wire up LangSmith tracing (`LANGCHAIN_TRACING_V2=true`) for dev-time
  debugging; the DB trace is the production source of truth regardless.
- Surface this as a "view reasoning trace" expandable panel in the frontend
  investigation UI (Phase 13.3).

**Files**: `prisma/schema.prisma`, new `src/models/agentRun.repository.ts`,
`src/modules/ai/services/ai-orchestrator.service.ts`.

---

### 8.4 [P1, M] Failed embeddings are silently and permanently unsearchable

**Problem**: [embedding.service.ts:36-41](traceIQ-backend/src/modules/ai/embedding.service.ts:36)
catches OpenAI failures and returns `[]` so the event write still succeeds — good for
availability, but that event's embedding is never generated again. No backfill job exists.

**Fix**: Add a lightweight backfill worker/script:
`SELECT id FROM audit_events WHERE cardinality(embedding) = 0 ORDER BY createdAt LIMIT N`,
re-embed, update. Run on a schedule (cron or a BullMQ repeatable job). Also add retry with
backoff (2–3 attempts) inside `generateEmbedding` itself before giving up, since most
OpenAI failures are transient rate limits.

**Files**: `src/modules/ai/embedding.service.ts`, new
`src/jobs/backfillEmbeddings.job.ts`.

## Phase 9 — Dynamic Detection Engine (the "not rule-based" upgrade)

Keep the existing deterministic rules — they're cheap, explainable, and good at known
patterns. Add an adaptive layer alongside them; combine both into one risk score.

### 9.1 [P1, M] Move rule thresholds out of code

**Problem**: Thresholds (`5` failed logins, `1000` records, `8–18` hours) are hardcoded in
[detection.rules.ts](traceIQ-backend/src/modules/detection/detection.rules.ts). No tenant
can tune sensitivity, and every change needs a redeploy.

**Fix**: New `DetectionRuleConfig` table: `tenantId, ruleName, enabled, params (Json)`.
Rules read their thresholds from this config (fall back to sane defaults if no row
exists) instead of literals. Expose via a `/api/v1/detection-rules` admin endpoint +
Phase 13 settings UI.

**Files**: `prisma/schema.prisma`, `src/modules/detection/detection.rules.ts`,
`src/modules/detection/detection.engine.ts`, new
`src/models/detectionRuleConfig.repository.ts`, new routes/controller.

---

### 9.2 [P2, L] Per-actor online behavioral baselining

**Problem**: All current rules use one global threshold for every actor in every tenant.
An actor who normally exports 50 records and one who normally exports 5,000 are held to
the identical `>1000` bar.

**Fix**: Maintain rolling per-`(tenantId, actor)` statistics — event volume/hour, action
mix, typical active hours — using an online algorithm so you never need to reprocess
history:
- **Welford's algorithm** for streaming mean/variance (no need to store raw samples).
- Or an **EWMA** (simpler, naturally forgets stale behavior, one line per update).

Store as a small Redis hash or a `ActorBaseline` Postgres table, updated by the worker
alongside `runDetections()`. Add a new stateless-style rule/signal:
`z = (currentValue - mean) / stddev`; flag when `|z|` exceeds a tunable threshold
(itself in `DetectionRuleConfig` from 9.1). This is the direct fix for "rigid thresholds
don't scale per actor."

**Files**: new `src/modules/detection/baseline.service.ts`, `prisma/schema.prisma` (if
persisting to Postgres instead of Redis-only), `src/workers/events.worker.ts`
(update baseline after every event), `src/modules/detection/detection.engine.ts`
(new anomaly signal alongside rule evaluation).

---

### 9.3 [P2, M] Reuse embeddings for semantic anomaly detection

**Problem**: You already pay for an OpenAI embedding per event
([events.worker.ts:61-64](traceIQ-backend/src/workers/events.worker.ts:61)) but only use
it for RAG search. It's also a free anomaly signal that no hand-written rule can express.

**Fix**: Maintain a rolling centroid vector per `(tenantId, actor)` (running average of
their embeddings — cheap, no extra OpenAI calls). On each new event, compute cosine
distance from the actor's centroid; large distance = "semantically unusual action for
this actor," independent of any rule. Feed this into the composite score in 9.4.

**Files**: `src/modules/detection/baseline.service.ts` (extend from 9.2),
`src/workers/events.worker.ts`.

---

### 9.4 [P2, M] Composite risk score

**Problem**: Rule hits (9.1), the z-score anomaly signal (9.2), and the embedding-drift
signal (9.3) currently would live as three unrelated numbers. Analysts need one score.

**Fix**: Start with a hand-weighted ensemble (no training required yet):
`risk = w1*ruleHit + w2*zScoreAnomaly + w3*embeddingDrift`, clipped to 0–100, surfaced on
`Detection.metadata.riskScore`. This is explicitly the bridge to Phase 10.4 — once you
have labeled outcomes, replace the hand-tuned `w1..w3` with weights learned from a small
logistic regression, without changing the shape of the pipeline.

**Files**: `src/modules/detection/detection.engine.ts`,
`src/modules/detection/risk-score.service.ts` (new).

---

### 9.5 [P2, S] Wire the existing feedback loop that's currently a dead column

**Problem**: `Detection.status` (`OPEN → ACKNOWLEDGED → RESOLVED`) already exists in the
schema but nothing reads it back anywhere. Analyst resolutions are exactly the labeled
data described in Phase 10.

**Fix**: Add a `Detection.resolution` enum (`TRUE_POSITIVE | FALSE_POSITIVE`) captured
when an analyst resolves a detection from the frontend (Phase 13). Every resolution
writes a row to a `DetectionLabel` table (or reuses `Detection` itself) — this becomes
the training set for 10.4.

**Files**: `prisma/schema.prisma`, `src/controllers/detection.controller.ts`
(add resolve endpoint if missing), Phase 13 frontend detection detail panel.

## Phase 10 — ML Data Strategy

This directly answers "where do I get training data."

### 10.1 [P1, L] Synthetic traffic + attack generator

**Problem**: No historical incident data exists, and won't until real tenants have real
incidents. Waiting for that blocks everything.

**Fix**: Build a standalone script (`scripts/generate-synthetic-events.ts`) that, against
a seeded demo tenant, produces:
- **Normal traffic**: plausible logins/CRUD/exports at realistic hourly distributions,
  varied per simulated actor "persona" (so baselining in 9.2 has something to baseline).
- **Labeled attack sequences**, injected at known points in the timeline and tagged in a
  side file/table for eval: credential-stuffing bursts, slow-drip brute force (the exact
  case that exposes the 7.4 bug), bulk exfiltration, off-hours admin sprees,
  privilege-escalation chains.

This gives you: (a) data to validate the 7.4 fix and the 9.2/9.3 anomaly signals against
known-bad patterns, (b) a repeatable precision/recall benchmark, (c) something to demo.

**Files**: new `scripts/generate-synthetic-events.ts`, new
`scripts/synthetic-scenarios/*.ts` (one file per attack pattern), new
`scripts/eval-detection-pipeline.ts` (replays the generator's labels against what the
engine actually flagged, reports precision/recall/latency).

---

### 10.2 [P1, S] Weak-label bootstrap from existing rules

**Fix**: Every event currently flagged by the deterministic rules is a noisy positive
label, free today. Combine with 10.1's synthetic labels as the initial training set for
10.4 — don't wait for real analyst feedback (9.5) to start.

**Files**: covered by 9.5's `DetectionLabel` table — source can be `RULE`, `SYNTHETIC`,
or `ANALYST`.

---

### 10.3 [P2, M] Label store + eval harness

**Fix**: Formalize `DetectionLabel(tenantId, eventId/detectionId, source, outcome,
features Json, createdAt)`. Build `scripts/eval-detection-pipeline.ts` to run against it
on demand — this is what tells you whether Phase 9's changes actually improved detection
quality, not just whether the code compiles.

**Files**: `prisma/schema.prisma`, `scripts/eval-detection-pipeline.ts`.

---

### 10.4 [P2, M] Train the risk-score weights once labels exist

**Fix**: Once `DetectionLabel` has enough rows (dozens–low hundreds, not thousands — this
is a 3–6 feature logistic regression, not a deep model), fit weights offline (a small
Python/scikit-learn notebook or even a plain JS gradient-descent script is enough) and
replace the hand-tuned `w1..w3` in 9.4 with the learned coefficients. Re-run
periodically as more labels accumulate; no live training infra needed at this scale.

**Files**: `src/modules/detection/risk-score.service.ts` (load weights from config
instead of hardcoding), new `scripts/train-risk-weights.ts`.

## Phase 11 — Frontend: SaaS Foundations

The current frontend ([App.tsx](traceIQ-frontend/src/App.tsx)) is functionally complete
(landing, login, dashboard, events, detections, actor profile, users, settings) but reads
as a generic AI-generated shell: no version control, no real signup funnel, no API key
management UI despite the backend having a full `apikeys` module, and a "product tour"
that's really just a static 4-slide modal.

### 11.1 [P0, S] Frontend has no git history

**Problem**: `traceIQ-frontend/` is not a git repository at all — confirmed via
`git status` failing with "not a git repository." Every change so far is unversioned.

**Fix**: `git init`, add a `.gitignore` (already exists, verify it covers `node_modules`,
`dist`), initial commit, then treat it like a real repo going forward (this also unlocks
actually reviewing frontend diffs in `/code-review`).

```bash
cd traceIQ-frontend
git init
git add -A
git commit -m "Initial commit: import existing TraceIQ frontend"
```

---

### 11.2 [P0, M] Real self-serve workspace signup

**Problem**: The landing page's only CTA is "Sign In" — there is no "Start Trial" /
"Create Workspace" path, and even the backend's `/register` endpoint currently requires
an existing `tenantId` (see 7.2), so no true self-serve signup exists end-to-end today.

**Fix**: Build a `SignupPage` that calls the new tenant-creation flow from 7.2 — company
name → creates `Tenant` + first `TENANT_ADMIN` `User` in one call → auto-login → lands in
the Phase 12 setup checklist instead of an empty dashboard. Add "Start Free Trial" as the
primary landing-page CTA, keep "Sign In" secondary. Add a separate "Invite teammate" flow
in Settings/Users using the invite-token mechanism from 7.2.

**Files**: new `src/pages/public/SignupPage.tsx` + `.css`, `src/App.tsx` (new route),
`src/pages/public/LandingPage.tsx` (CTA), `src/api/auth.api.ts` (new), backend 7.2.

### 11.3 [P1, M] API key management UI

**Problem**: The backend has a full `apikeys.controller.ts` / `apikeys.routes.ts` module
(create/list/revoke tenant API keys — this is how source services actually authenticate
to `POST /api/v1/events`), but there's no corresponding frontend page. A new tenant has
no way to get their ingestion key without hitting the API directly.

**Fix**: New `ApiKeysPage` (or a section inside `SettingsPage`) — list keys (masked,
show-once-on-creation pattern like Stripe/GitHub), create, revoke, with copy-to-clipboard
(there's already a `CopyButton` shared component to reuse). This is not just UX polish —
without it, a self-serve signup (11.2) leads to a dead end where the customer can log in
but has no way to actually send events.

**Files**: new `src/pages/app/ApiKeysPage.tsx` + `.css`, new `src/api/apikeys.api.ts`,
`src/App.tsx` (route), `src/components/layout/Sidebar.tsx` (nav entry).

### 11.4 [P3, M] Design system consistency pass

**Problem**: Each page/component ships its own `.css` file
(`DashboardPage.css`, `EventsPage.css`, `Shared.css`, etc.) with no shared design tokens
visible at a glance — typical of iteratively AI-generated pages where each screen was
styled in isolation.

**Fix**: Extract a single `src/styles/tokens.css` (color scale, spacing scale, radius,
shadow, typography) that every page/component consumes via CSS variables. Add a light/dark
theme toggle backed by these tokens (SaaS-standard expectation, currently absent entirely).
This is prerequisite work for Phase 13's polish items looking coherent rather than bolted-on.

**Files**: new `src/styles/tokens.css`, touches every `*.css` file to consume variables
instead of hardcoded hex values.

## Phase 12 — Frontend: Onboarding & Activation

### 12.1 [P1, M] Replace the passive tour with an actionable setup checklist

**Problem**: [OnboardingWizard.tsx](traceIQ-frontend/src/components/onboarding/OnboardingWizard.tsx)
is a 4-slide "here's what the dashboard does" modal, dismissed once via `localStorage`,
that explains features rather than getting the user to a working state. Real SaaS
onboarding (Linear, Vercel, Stripe) is a checklist of *actions*, not a slideshow.

**Fix**: Replace with a persistent (dismissible, but reappearing until complete) setup
checklist tied to real backend state, not just `localStorage`:
1. ☐ Create your first API key (links to 11.3)
2. ☐ Send your first event (show a copy-pasteable `curl`, poll for the first event to
   arrive, confetti/success state when it does)
3. ☐ Invite a teammate (optional, skippable)
4. ☐ View your first detection (auto-generated by seeding a demo event if the tenant has
   zero events after N minutes — see 12.3)

Track completion server-side (`Tenant.onboardingState Json` or a dedicated table) so it's
consistent across devices/sessions, not per-browser `localStorage`.

**Files**: rewrite `src/components/onboarding/OnboardingWizard.tsx` →
`SetupChecklist.tsx`, `prisma/schema.prisma` (onboarding state), new backend endpoint to
read/update it.

---

### 12.2 [P2, M] Empty states that drive action, not just say "no data"

**Problem**: Need to verify current empty-state copy in `EmptyState.tsx`
([components/shared](traceIQ-frontend/src/components/shared/EmptyState.tsx)) — generic
empty states ("No events yet") are a classic AI-generated-app tell.

**Fix**: Every empty state should name the specific next action for *that* page: Events
page empty → "Send your first event" with the curl snippet inline; Detections page empty
→ "No threats detected yet — that's good! Rules are watching for X, Y, Z"; Users page
empty (impossible, always ≥1 admin) → n/a. Make empty states context-aware of onboarding
progress from 12.1.

**Files**: `src/components/shared/EmptyState.tsx`, each page consuming it.

### 12.3 [P2, M] Demo/sample data seeding for new tenants

**Problem**: A brand-new tenant has an empty dashboard, empty charts, nothing to click —
worst possible first impression, and nothing to show a reviewer/interviewer without
manually curling events first.

**Fix**: On tenant creation (11.2), optionally seed ~50–100 realistic historical events
(reuse the Phase 10.1 synthetic generator, scaled down) plus 2–3 pre-triggered detections,
clearly labeled `[DEMO]` and easy to bulk-delete once real data arrives. This turns "empty
dashboard" into "working product" from second one.

**Files**: reuses `scripts/generate-synthetic-events.ts` from 10.1, new backend seeding
call in the tenant-creation flow (11.2).

## Phase 13 — Frontend: UX / Product Polish

### 13.1 [P2, L] Real-time live feed instead of polling

**Problem**: Need to confirm current [LiveFeed.tsx](traceIQ-frontend/src/components/dashboard/LiveFeed.tsx)

`LiveFeed` subscribes via `EventSource` and prepends new rows with a subtle highlight
animation.

**Files**: new backend SSE route/controller, `src/workers/events.worker.ts` (publish
hook), `src/components/dashboard/LiveFeed.tsx`.
