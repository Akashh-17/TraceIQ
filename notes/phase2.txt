KEY CONCEPTS TO REMEMBER
-------------------------

1. CONTROLLER → SERVICE pattern
   Think of it like a restaurant:
   - Controller = Waiter    (takes order from customer, brings food back)
   - Service    = Chef      (does the actual cooking — business logic)
   - Controller NEVER cooks. Service NEVER talks to the customer.

   Why split? Because in Phase 6 the service will push to a queue instead of
   writing to DB. The controller code won't change at all.

2. ZOD VALIDATION
   Zod does two jobs at once:
   a) Runtime: rejects bad requests before they hit your service
   b) Compile-time: z.infer<typeof Schema> gives you a TypeScript type for free
   You never write a separate interface — Zod generates it.

   CreateEventSchema.safeParse(req.body)
   → success: true  → result.data is typed and safe
   → success: false → result.error tells you exactly which field failed

3. AppError vs regular Error
   Regular JS Error: has message, name, stack. No HTTP concept.
   AppError extends Error and adds:
   - statusCode → which HTTP code to send (404, 400, 500...)
   - isOperational → was this expected? (wrong password = yes, DB crash = no)

   Unexpected errors get logged loudly. Operational errors just get a clean response.

4. WHY 202 AND NOT 201
   201 = "Resource created RIGHT NOW"
   202 = "Request accepted, will be processed"
   Since Phase 6 will queue the event (async), nothing is created immediately.
   202 is the honest answer. We set it now so Phase 6 needs zero changes here.

5. env.ts pattern
   requireEnv("KEY") crashes the app at startup if a variable is missing.
   This is intentional — better to crash immediately with a clear message
   than to fail silently 3 hours later on a production request.
